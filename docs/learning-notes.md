# 학습 개념 정리 — 이해한 내용을 설명하기 위한 복습 노트

이 문서는 실제 수행 보고서의 개념을 쉽게 풀어 쓴 설명 자료이다. 아래에 등장하는 추가 예시는 실행 결과를 주장하는 로그가 아니다. 실제 명령과 출력은 각 단계 보고서에 기록했다.

## 1. Ubuntu는 무엇인가?

Ubuntu는 Linux를 기반으로 만든 운영체제이다. Windows처럼 파일을 관리하고 프로그램을 실행할 수 있다. 현재 실습에서는 Windows를 사용하면서 WSL2를 통해 Ubuntu 환경도 함께 실행한다.

| 이름 | 역할 |
|---|---|
| Windows | 평소 PC에서 사용하는 호스트 운영체제 |
| WSL2 | Windows에서 Linux 환경을 실행하는 기능 |
| Ubuntu | 이번 Linux 실습을 수행하는 운영체제 환경 |
| Bash | Ubuntu에서 입력한 명령을 해석하는 쉘 |

Ubuntu 자체가 터미널이나 명령어인 것은 아니다. Ubuntu도 그래픽 화면으로 사용할 수 있지만, 이번 실습에서는 명령어를 입력하는 방식을 사용했다.

## 2. 폴더는 왜 만드는가?

서류철에 관련 서류를 모으듯이, 파일을 목적에 맞게 묶어 찾고 관리하기 위해 만든다. 디렉터리는 폴더를 의미한다.

이번에는 2단계 파일을 mission-step2에, 3단계 대상을 mission-step3에 모았다. 실습 대상을 구분하면 다른 파일과 혼동하지 않고 결과를 확인할 수 있다.

## 3. 파일 내용을 왜 읽는가?

파일이 공책이라면 파일 읽기는 공책을 펼쳐 내용을 확인하는 것이다. 파일 이름만으로는 실제 저장된 내용을 알 수 없으므로 작성·복사 후 내용을 확인한다.

이번 실습에서는 notes.txt에 글을 저장한 뒤 cat으로 두 줄을 읽었다. 복사본에서도 같은 내용을 확인했으므로 복사 결과의 내용까지 검증했다.

| Windows에서 익숙한 작업 | 이번 Ubuntu 실습에서 수행한 작업 |
|---|---|
| 새 폴더 만들기 | mkdir로 디렉터리 생성 |
| 폴더 더블클릭해서 들어가기 | cd로 현재 작업 위치 이동 |
| 폴더 안 목록 보기 | ls로 항목 조회 |
| 메모장으로 글 읽기 | cat으로 텍스트 내용 확인 |

명령어를 입력했는지만 보는 대신, 현재 위치·목록·파일 내용을 확인하여 실제 결과를 검증했다.

## 4. 절대 경로와 상대 경로는 어떻게 다른가?

절대 경로는 전체 주소, 상대 경로는 현재 위치에서 출발하는 길 안내에 가깝다.

| 현재 위치 | 상대 경로 | 같은 파일의 절대 경로 |
|---|---|---|
| /home/user/mission-step2 | ./notes.txt | /home/user/mission-step2/notes.txt |
| /home/user | mission-step2/notes.txt | /home/user/mission-step2/notes.txt |

이번 실습에서 두 방식으로 같은 두 줄을 읽었다. 현재 위치가 바뀌면 길 안내인 상대 경로는 바뀌지만, 같은 파일의 전체 주소는 그대로였다.

- 점 하나는 현재 디렉터리이다.
- 점 두 개는 상위 디렉터리이다.
- 물결표는 쉘에서 사용자 홈 경로를 나타낸다. 이번 홈 경로는 /home/user이다.

## 5. 일반 파일과 디렉터리는 어떻게 다른가?

| 구분 | 일반 파일 | 디렉터리 |
|---|---|---|
| 쉬운 비유 | 내용이 적힌 서류 | 서류를 모으는 서류철 |
| 역할 | 내용 저장 | 파일·하위 디렉터리 항목 관리 |
| 이번 대상 | permission-file.txt | permission-dir |
| 목록의 종류 표시 | 맨 앞이 - | 맨 앞이 d |

빈 파일도 파일이다. permission-file.txt는 내용이 없는 상태로 권한 변경을 실습했다.

## 6. 권한은 왜 필요한가?

누가 읽고, 수정하고, 실행·접근할 수 있는지 구분하기 위해 필요하다. 집의 열쇠와 비슷한 비유를 사용할 수 있지만, 실제 Linux에서는 사용자·그룹과 각 권한을 기준으로 접근을 판단한다.

| 권한 | 파일 | 디렉터리 |
|---|---|---|
| r, 4 | 내용 읽기 | 내부 항목 이름 목록 읽기 |
| w, 2 | 내용 수정 | 내부 항목 생성·삭제·이름 변경에 관여 |
| x, 1 | 프로그램·스크립트 실행 | 접근·통과 |

숫자 세 자리는 소유자, 그룹, 기타 사용자 순서이다. 644는 소유자 읽기·쓰기와 나머지 읽기, 755는 소유자 읽기·쓰기·실행 또는 접근과 나머지 읽기·실행 또는 접근이다. 이번 755 대상은 디렉터리이므로 x를 접근·통과로 설명한다.

파일 안의 내용을 바꾸는 것과, 부모 디렉터리에서 그 파일 항목을 삭제하는 것은 다른 작업이다. 그래서 파일의 쓰기 권한이 없다는 사실만으로 삭제가 항상 불가능하다고 판단할 수는 없다.

## 7. 스크립트는 무엇인가?

컴퓨터가 순서대로 실행할 명령을 적어둔 파일이다. 반복 작업의 지시서와 비슷하다. 한 줄씩 입력하던 명령을 파일로 묶어 사용할 수 있다.

**개념 설명용 예시 — 이번 실습에서 생성·실행한 결과가 아님**

```bash
#!/bin/bash
echo "실습을 시작합니다."
echo "실습을 마쳤습니다."
```

첫 줄은 직접 실행할 때 사용할 해석기를 지정한다. Bash 스크립트를 경로로 직접 실행하는 방식과 Bash에 파일을 읽도록 넘기는 방식은 다르다.

**아래 명령도 방식 설명용 예시이며 실행 증거가 아니다.**

```bash
./example.sh
bash example.sh
```

첫 방식은 파일의 실행 권한 등이 필요하다. 두 번째는 Bash가 스크립트를 읽으므로 파일 자체의 x 권한이 없어도 읽기·경로 접근 조건 등이 갖춰지면 실행할 수 있다. 단순히 확장자가 sh인 것만으로 실행 가능 여부가 결정되지는 않는다.

## 8. Git과 GitHub는 어떻게 다른가?

| 구분 | Git | GitHub |
|---|---|---|
| 역할 | 로컬 변경 이력 관리 | 원격 저장소 호스팅과 협업 |
| 대표 작업 | 변경 선택, 커밋, 이력 조회 | 원격 공유, PR, 이슈 |

Git 설치, 작성자 정보 설정, GitHub 로그인, 원격 업로드는 서로 다른 확인 항목이다. 지금은 Windows Git 설치와 버전 조회를 검증했으며, 설정·인증·푸시 성공은 이후 실제 증거가 필요하다.

## 10. Docker 이미지·컨테이너·주 프로세스

이미지는 실행 환경을 만드는 틀이고, 컨테이너는 그 틀로 만든 개별 실행 공간이다. 이번에는 ubuntu:24.04 이미지로 mission4-ubuntu 컨테이너를 만들었다.

| 동작 | 실제 관찰 |
|---|---|
| 주 Bash 종료 | 컨테이너도 중지됨 |
| exec의 추가 Bash 종료 | 원래 Bash가 살아 있어 컨테이너 유지 |
| attach 연결 분리 | 연결만 끊어져 컨테이너 유지 |
| stop 후 start | 같은 컨테이너 ID로 재시작 |

터미널이 연결되어 있다는 것과 주 프로세스가 실행 중이라는 것은 다르다. Docker Desktop이 관리하는 엔진에 WSL Ubuntu의 Docker CLI로 요청을 보내고, 컨테이너 내부에서는 그 컨테이너에 설치된 명령을 사용한다.

## 11. Nginx 베이스에 내 웹 페이지를 더하기

Nginx는 HTML 등을 브라우저에 전달하는 웹 서버이다. 이번에는 공식 이미지의 웹 서버 설치·시작 설정을 활용하고, 내가 만든 HTML을 웹 루트로 복사했다.

| 항목 | 이번 실습의 의미 |
|---|---|
| FROM | Nginx가 준비된 베이스를 선택 |
| COPY | app의 웹 페이지를 이미지 내부 웹 루트로 복사 |
| mission-web:v1 | 만들어진 이미지 이름·태그 |
| mission-web | 실행한 컨테이너 이름 |
| 8080:80 | 호스트의 8080번과 컨테이너의 80번 포트 연결 |

빌드 완료, 실행 상태, HTTP 응답은 각각 다른 검증이다. 이번에는 FINISHED 출력, Up 상태, HTTP 200과 실제 HTML 본문을 모두 확인했다.

호스트 HTML을 수정하는 것과 이미지 안에 복사된 HTML은 별개이다. 5단계 방식에서는 수정 후 재빌드하고 새 이미지로 컨테이너를 만들어야 반영된다. 6단계에서는 바인드 마운트로 호스트 파일을 연결해 그 차이를 확인했다.

## 12. 바인드 마운트의 변경 반영

호스트 폴더를 컨테이너의 웹 루트에 연결하면 Nginx가 연결된 파일을 읽을 수 있다. 이번에는 호스트 파일을 수정한 뒤 같은 localhost:8081에서 Updated 제목과 Mission 6 문구를 확인했다.

readonly 설정은 컨테이너의 쓰기를 제한한다. 호스트 소유자가 원본 파일을 수정하는 작업과는 구분된다. 실제 RW=false인 연결에서 호스트 수정 내용이 반영됐다.

호스트·컨테이너 파일과 HTTP 본문, 브라우저 화면, 컨테이너 상태를 함께 확인해 옵션 이름만으로 성공을 판단하지 않았다. 바인드 마운트 변경 반영과 Docker 볼륨의 영속성은 별개이므로 7단계에서 볼륨을 따로 검증했다.

[실제 바인드 마운트 검증](06-port-bind-mount.md)

## 13. 컨테이너를 삭제해도 볼륨 파일이 남는 이유

컨테이너가 작업 공간이라면, 이름 있는 볼륨은 별도로 보관하는 저장함에 가깝다. 첫 작업 공간을 삭제한 뒤 새 작업 공간에 같은 저장함을 연결해 이전 파일을 읽었다.

실제로 mission7-first를 삭제하고 새 ID의 mission7-verify를 생성했다. 두 컨테이너가 연결한 볼륨 이름은 mission-data로 같았고, 새 컨테이너에서 파일을 쓰지 않고 같은 문장을 읽었다.

stop은 중지이고 rm은 컨테이너 삭제이다. 이번에는 두 작업을 구분하여 삭제 이후 데이터를 확인했다. 기존에 있던 mission7-second를 새 컨테이너라고 가정하지 않고 다른 이름으로 새 검증 대상을 만들었다.

볼륨도 삭제하거나 데이터가 손상되면 그 데이터를 잃을 수 있다. 영속성은 실행 환경과 데이터 수명을 분리하는 것이며, 별도 복사본을 만드는 백업을 자동으로 제공한다는 뜻은 아니다.

[실제 볼륨 영속성 검증](07-volume-persistence.md)


## 14. 로컬 커밋과 원격 게시 구분

학습자가 로컬 main에서 커밋 1edb655를 만들었다. 이것은 파일을 Git 이력에 보관한 결과이며 GitHub main 업로드와는 다르다. fetch는 원격 기록을 받아오고, restore는 지정한 기록의 파일을 작업 폴더에 놓으며, push는 로컬 커밋을 원격으로 보낸다.

사진이 화면에 보인다는 사실과 저장소의 파일 경로에 저장됐다는 사실도 구분했다. 실제 파일을 찾아 docs/images로 복사한 뒤 문서의 상대 경로로 연결했다.
